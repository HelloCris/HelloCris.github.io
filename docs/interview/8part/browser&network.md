# 浏览器/网络问题

## 三种会话保持机制

::: info session 机制保持会话

**存在的问题**

- 高并发情况下，会占用服务器大量内存。
- 分布式（一个业务分成几个子业务，部署在多个服务器）或者集群（一个业务部署在多个服务器）的时候，session 不能共享。

**解决方案**

- 高并发的时候可以将 session 存储到 redis，如果用户长时间没有访问，将 session 存储到 redis，就减少了服务器的压力。
- 分布式或者集群的时候，先通过 redis 来判断用户状态也可以实现 session 共享。

:::

::: info cookie 机制保持会话

**使用方法**

- 登录验证后，创建登录凭证（比如：用户 id + 登录时间 + 过期时间），将登录凭证进行加密（为了避免暴露信息），加密后写到浏览器的 cookie，以后每次请求都发送 cookie，服务器根据对应的解密算法对其进行验证（或者将加密过的 cookie 内容存储到数据库，请求服务器的时候，服务器在数据库进行查找）。

**存在的问题**

- 每次访问都提交 cookie，增加请求量。
- 其他访问可能需要 cookie（比如说购物车的信息存放在 cookie），浏览器对每个域存储的 cookie 的大小有限制，那么需要控制加密后的凭证。

:::

::: info token 机制保持会话

**使用方法**

- cookie 和 session 依赖于浏览器，如果客户端不是浏览器，那么需要手动添加 token（和 cookie 类似，也是登录凭证），将 token 添加到 http header 或者作为参数添加到 url。

**存在的问题**

- 每次访问的时候手动添加 token。
- 和 cookie 的方式一样增加了请求量。

:::

## 网络五层/七层模型

相关笔记链接：[网络层级 - OSI 七层模型](/notes/others/network.html#网络层级-osi-七层模型)

**五层模型：**

> 物理层 → 数据链路层 → 网络层 → 传输层 → 应用层

**七层模型：**

> 物理层 → 数据链路层 → 网络层 → 传输层 → 会话层 → 表示层 → 应用层

| 层次           | 主要功能                                                         | 数据单位        | 典型协议/设备                                |
| -------------- | ---------------------------------------------------------------- | --------------- | -------------------------------------------- |
| **应用层**     | 为用户应用程序提供网络服务，如网页访问、邮件、文件传输、域名解析 | 报文 / 消息     | HTTP、HTTPS、FTP、SMTP、DNS、SSH；代理服务器 |
| **传输层**     | 提供端到端通信，负责分段、端口寻址、可靠传输或不可靠传输         | 报文段 / 数据段 | TCP、UDP；防火墙、网关                       |
| **网络层**     | 负责逻辑寻址和路由选择，把数据从源主机送到目的主机               | 分组 / 数据包   | IP、ICMP、ARP；路由器                        |
| **数据链路层** | 负责相邻节点之间的帧传输、物理寻址、差错检测                     | 帧              | Ethernet、PPP、Wi-Fi；交换机、网桥           |
| **物理层**     | 负责比特流在物理介质上的传输，定义电气、机械、功能特性           | 比特            | 网线、光纤、无线电波；集线器、中继器         |

## 强制缓存 和 缓存协商

**强制缓存**与**缓存协商**是浏览器 HTTP 缓存机制的两种核心策略，分别对应**强缓存**和**协商缓存**。两者配合使用，能最大程度减少不必要的网络请求，提升页面加载速度。

```
请求资源
  ⬇️
强缓存是否命中？（Cache-Control / Expires）
  ├── 是 → 直接使用本地缓存（200 from cache）
  └── 否 → 发起请求，携带 ETag / Last-Modified
              ⬇️
        服务器比对
          ├── 资源未变 → 304 Not Modified（使用本地缓存）
          └── 资源已变 → 200 + 新资源 + 新缓存头
```

### 强缓存

强缓存是指浏览器直接从本地缓存中读取资源，**完全不向服务器发送请求**。是否命中强缓存，由响应头中的两个字段控制：

1. `Cache-Control`（优先级更高）

| 值             | 含义                                                   |
| -------------- | ------------------------------------------------------ |
| `max-age=3600` | 资源在 3600 秒内有效，直接使用缓存                     |
| `no-cache`     | 不使用强缓存，但**会走协商缓存**（注意：不是"不缓存"） |
| `no-store`     | 完全不缓存，每次都重新请求                             |
| `public`       | 允许浏览器和中间代理都缓存                             |
| `private`      | 仅允许浏览器缓存，代理不可缓存                         |

2. `Expires`（HTTP/1.0 遗留，优先级低于 Cache-Control）

- 指定一个绝对过期时间，如 `Expires: Wed, 13 Aug 2027 15:00:00 GMT`
- 受客户端本地时间偏差影响，可靠性不如 `Cache-Control`

> **流程**：浏览器判断强缓存是否过期 → 未过期则直接使用本地缓存（状态码 `200 from disk/memory cache`），不发起网络请求。

### 协商缓存

当强缓存失效（或设置了 `no-cache`）时，浏览器会向服务器发起请求，但会携带缓存标识，由服务器判断资源是否更新：

1. `ETag` / `If-None-Match`（优先级更高）

- 服务器首次返回资源时，生成一个唯一标识 `ETag: "abc123"`
- 后续请求携带 `If-None-Match: "abc123"`
- 服务器比对：未变化返回 **`304 Not Modified`**（无 body），变化则返回 **`200`** + 新资源

2. `Last-Modified` / `If-Modified-Since`（HTTP/1.0）

- 服务器返回资源最后修改时间 `Last-Modified: Wed, 13 Aug 2026 10:00:00 GMT`
- 后续请求携带 `If-Modified-Since: Wed, 13 Aug 2026 10:00:00 GMT`
- 服务器比对时间：未变化返回 304，变化返回 200

> ETag 比 Last-Modified 更精确，因为后者以秒为单位，且文件内容不变但修改时间变了会误判。

## cookie 与 session

相关笔记链接：[session](/notes/nodejs/base.html#session)

> **核心结论**：cookie 存放在客户端（浏览器），用于"记住"用户信息；session 存放在服务端内存中，用于"识别"用户身份。两者常常配合使用：session 用一个 sessionId 标识用户，这个 id 一般通过 cookie 在前后端之间传递。

::: info 什么是 cookie

1. cookie **由服务端创建**（在响应头 `Set-Cookie` 中下发），最终**保存在浏览器端**。
2. cookie 的生命周期可通过 `cookie.setMaxAge(2000)` 设置（单位：秒）。
   - **不设置过期时间**：cookie 生命周期为会话级，浏览器关闭即销毁。
   - **设置了过期时间**：即使浏览器关闭，cookie 也会被持久化到磁盘，到期才消失。
3. 同一个 cookie 可以被**多个浏览器窗口**共享（同一域下的多个标签页共用一份 cookie）。
4. 同一个 Web 应用可以保存**多个 cookie**，但这些 cookie 都归属于同一个域下的 cookie 文本。
5. cookie **默认以明文方式存储在客户端**，因此安全性较低，敏感字段建议 MD5/加密后再存放。
6. 每次请求都会携带与当前站点相关的 cookie 数据，**用户可在浏览器中直接看到 cookie 内容**，所以**不要在 cookie 中存放敏感数据**（如明文密码、未加密的用户 id 等）。

:::

::: info 什么是 session

1. session **存放在服务端的内存中**（也可持久化到数据库、Redis 等）。
2. **一个用户的浏览器独享一个 session 对象**（通过 sessionId 区分）。
3. session 中属性的默认寿命是 30 分钟，可通过项目配置文件修改。
4. 服务端能为不同的浏览器提供不同的 session —— 因为每个浏览器访问站点时，若发出的 HTTP 请求没有携带 `JSESSIONID`，服务端就会自动创建一个新的 session 并把 id 返回。
5. session 的开启需要依赖服务器环境，**部分场景需要提前确认是否存在与 session 相关的表 / 配置文件**（如 Java Web 中需要在 `web.xml` 中配置 session-config）。

:::

| 对比维度     | cookie                                                 | session                                                                              |
| ------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **存放位置** | 存放在客户端浏览器的临时文件里（可被读取）             | 存放在服务端的内存中                                                                 |
| **安全性**   | 明文存储在客户端，安全性较差，建议加密后再存放         | 存放于服务端内存，安全性更高                                                         |
| **网络传输** | 每次请求都会把 cookie 信息回传服务器，增加请求量       | session 自身的属性值不会传给客户端，只传 sessionId                                   |
| **生命周期** | **累计时间**（从创建到过期时间为止，浏览器关掉也计时） | **间隔时间**（默认 30 分钟无操作就失效）                                             |
| **失效情况** | 到达过期时间 / 用户手动清除                            | ① 关闭服务器；② 重新部署 Web 应用；③ 设置的固定时间到；④ 服务器异常导致 session 丢失 |
| **占用资源** | 占用少量客户端存储                                     | 占用服务端内存，高并发时压力较大（可结合 Redis 解决）                                |
| **作用范围** | 同一域下**可被多个浏览器/标签页共享**                  | **单用户独享**（一个 session 对应一个浏览器会话）                                    |

## 重定向

重定向即网页自动跳转，分 **301（永久）** 和 **302（临时）** 两种：

- **301**：新网址继承旧网址排名，旧网址排名清零。
- **302**：旧网址排名不变，新网址无排名。

**为什么推荐301重定向？**

1. **利于SEO**：域名变更时，外部链接和排名能完美转移到新网址；多域名指向主域时，也不影响排名。
2. **302的弊端**：除Google外，大多数搜索引擎会分散外链权重，导致主站排名下降。

**结论**：**301永久性重定向**是最安全、最理想的SEO解决方案。

## `fetch` 请求方法

`fetch` 是浏览器原生提供的**网络请求 API**（基于 WHATWG Fetch 标准，ES6 时代正式普及），用来替代老旧的 `XMLHttpRequest`。

```js
fetch(resource, options?) => Promise<Response>
```

```js
// 最简 GET
const res = await fetch("/api/user");
const data = await res.json();

// 带配置项的 POST
const res = await fetch("/api/login", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Tom", pwd: "123" }),
});
```

::: warning ⚠️ 注意
`fetch` 返回的是一个 **Promise**，且**只有网络层失败（断网、DNS 失败、跨域被拦）才会 reject**；HTTP 状态码（如 404、500）**不会**触发 reject，需要自己判断 `res.ok` 或 `res.status`。
:::

| 核心对象            | 关键属性 / 方法                                                                     | 说明                                   |
| ------------------- | ----------------------------------------------------------------------------------- | -------------------------------------- |
| `Response`          | `res.ok` / `res.status` / `res.statusText`                                          | `ok` = `status` 在 200–299             |
|                     | `res.headers`                                                                       | 响应头（Headers 对象）                 |
|                     | `res.json()` / `res.text()` / `res.blob()` / `res.arrayBuffer()` / `res.formData()` | 都是返回 Promise，用于解析不同格式体   |
|                     | `res.clone()`                                                                       | 响应体只能读一次，需多次读取时先 clone |
| `Request`（可省略） | `new Request(url, options)`                                                         | 可单独构造请求对象再传给 fetch         |

## html网页渲染的基本过程

```
HTML 字节流
   ↓ 解析
  DOM 树 ──┐
            ↓ 合并（Attachment）
CSS 字节流   →  CSSOM 树  →  渲染树(Render Tree)
            ↓
        布局 Layout（回流 Reflow）→ 计算每个节点几何位置
            ↓
        绘制 Paint（重绘 Repaint）→ 填充像素（颜色/文字/图片/阴影）
            ↓
        合成 Composite → 多图层合并上屏（GPU）
```
